## 1. 変更理由と実装範囲

11月27日の[改善資料](../RTC_Fallback_Log_ID_Improvement_Plan_20261127_Rev0.md)に基づき、RTCなし・日時取得失敗でもSDログを開始できるよう改修した。従来の数字14桁名とSD側の日時名検証の不整合を解消し、起動ごとに仮IDを初期化して既存ログと衝突する経路を防ぐ。

本書の書式・共通番号・衝突試行上限は、実装指示に基づく改修版の具体化である。製品側の正式仕様変更や量産受入の承認ではない。RTC-LOG-01～04はCloseせず、実機・運用上の残確認を継続する。

## 2. ログ名と試行番号

| 状態／用途 | 開始時の名前 | 同試行の有効S/Nを取得したTEST終了後 |
|---|---|---|
| RTC正常・TEST | `20261128_100000_T000123.csv` | `000001_20261128_100000_T000123.csv` |
| RTC異常・TEST | `NO_RTC_T000123.csv` | `000001_NO_RTC_T000123.csv` |
| RTC正常・CONT | `20261128_100000.csv` | 製品別のS/N付加は行わない |
| RTC異常・CONT | `NO_RTC_C000124.csv` | 開始時の名前を維持する |

番号は6桁以上で、999999の次は1000000。桁を切り捨てたり先頭へ巻き戻したりしない。ファイル名はASCIIの厳密な書式で認識し、255文字を超える名前はFILENAMEとして拒否する。S/Nは6桁の文字列として先頭ゼロを保持する。

日時付きTEST、仮ID TEST、仮ID CONTは共通の番号最大値を引き継ぐ。TESTの番号はtrial_idと一致する。CONTや未保存の予約により欠番が生じても詰め直さない。日時付きCONTは既存形式のままで、有番名へ変更しない。

## 3. RTC読取りと時刻不明の扱い

- RTCがNoneならNO_RTC。読取り時のValueError／OSError／RuntimeError／AttributeError／TypeErrorはREAD_ERRORとする。
- 文字列形式・ASCII数字・暦・2000～2099年・時分秒を既存RTCDateTimeで検証し、不正ならINVALIDとする。
- 正常に読めた場合だけ日時名を採用する。異常時は仮ID名を使い、CSVのtimestampには架空の日時・tick値・前回正常値を入れず空欄にする。
- 直近の読取り状態は`logger.rtc_filename_status`に保持する。新しいATEコマンド・CSV列は追加しない。RTCの診断とLoggerの保存成否は従来どおり分離する。
- 記録中のRTC復帰だけで開いているファイルを改名しない。以後の有効な時刻はCSVに使用できる。新しいファイルの開始・CONT分割時に、その時点のRTC状態で命名する。
- RTCのOSF・電池保持・実時刻との一致まで、暦検証だけで正常と保証するものではない。これらの運用判断と実機保持確認は残す。

## 4. 採番と既存ファイルの保全

1. マウント時の既存走査で両BANKの所有マーカー、使用中BANK、認識対象ログを確認する。
2. S/N付き名、旧日時TEST名、新しい仮ID名を共通パーサーで解析する。0 byteの正規名も使用済み番号として扱う。正規名と同名のディレクトリは対象外とする。
3. 両BANKと使用中BANKの確認がすべて成功した場合だけ`namespace_ready=True`とし、集計した番号を確定する。再走査の途中で失敗した場合も採番許可を取り消す。
4. FileSDSinkの`reserve_log_number()`は確認済み最大値・RAM最大値・指定下限の最大値＋1を予約する。マウント不良・未確認時はログIDを予約せず、ファイルを作らない。
5. 作成直前に両BANKの同名を確認し、ENOENT以外のI/Oエラーを「空き」と判断しない。BANK循環削除より前にこの確認を行う。
6. 有番名の同名衝突は次番号へ進む。最大8候補で打ち切ってFILE_EXISTSを報告し、無限に走査・再試行しない。日時付きCONTの同時刻衝突は既存のFILE_EXISTSとして扱う。

各開始時に両BANK全体を再走査する方式にはしていない。マウント時の完全な一覧と、単一Loggerによる以後の番号予約を使う。カードの外部書換えは停止・再マウントして確認し直す運用とする。実行中に別の書込み主体がS/N付きの別名を追加した場合まで、番号重複を検出する保証は含めない。

作成・名前変更は存在確認後に既存のファイルAPIを使い、独立した同時書込み主体を許可しない。存在確認と操作はファイルシステム上の原子的な排他操作ではない。MicroPython／FATの実電源断・破損時の挙動は未検証で、今回のHost成功だけで保証しない。

## 5. S/N付加、CONT分割、SD異常

TEST終了時は既存どおりQueue排出→flush→close→S/N付加の順とする。S/N未取得・不正時は開始名を残し、前試行のS/Nを流用しない。変更先の同名が他方BANKにある場合も拒否する。確認I/O・rename失敗時には元名を保持して保存異常を報告する。

CONTはRTCなしでも分割でき、分割先を同じ仮ID採番で生成する。RTC正常で同じ秒の名前しか作れない間は、従来どおりQueueを保持して次の日時を待つ。

SD異常・番号確認不能でもTEST_STARTの受付OKと試験期間管理は維持する。保存失敗はLogger状態・最終Self Check・破棄数へ反映し、製品PASS/FAILと分ける。確認不能時のRAM試行IDは試験期間を管理する識別子であり、SD保存された一意な仮IDが確保できたとみなさない。試験中の再マウント・自動復帰は追加しない。

保証対象は、正常に確認できた両BANKに残る認識対象ログである。削除済みログ・交換済みSDまで含む永久欠番、FAT破損からの修復、電源断直前の未保存行の復元は追加していない。
