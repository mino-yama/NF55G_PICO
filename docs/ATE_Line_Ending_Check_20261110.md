# ATE終端文字・CR単独の確認

日付: 2026-11-10

## 対象と確認範囲

ユーザー指定の `INFO<CR>`、`INFO<LF>`、`INFO<CR><LF>`、コマンドなしのCR定期送信を確認対象とする。特にCR単独の空コマンド誤認、無視の可否、次の正常コマンドへの影響を確認する。

現行ATE_Command_Masterは要求・応答の終端をCRLFと規定している。今回の確認はPC上の現行 `src/ate_server.py` と `FixtureApp` を使用した模擬受信であり、COM20の実機試験ではない。各入力後に100回service_onceを実行した。定期送信の実時間条件は未検証。実装・実機配置は変更していない。

## ホスト上で確認した事実

| 入力 | 応答・内部状態 | 次の正常コマンドへの影響 |
|---|---|---|
| `INFO<CR>` | 応答なし、CR後のLF待ちが残る | 次の `*IDN?<CR><LF>` が `ERR:FRAME`。さらに次の同コマンドは正常 |
| `INFO<LF>` | 応答なし、FRAME異常状態が残る | 次の `*IDN?<CR><LF>` が `ERR:FRAME`。さらに次は正常 |
| `INFO<CR><LF>` | 行として受理するが `ERR:UNKNOWN_CMD` | 次の正常コマンドは正常 |
| CR単独を3回、別々に入力 | 各回応答なし。受信中状態が残る | 直後の `*IDN?<CR><LF>` が `ERR:FRAME`。さらに次は正常 |
| 空の `<CR><LF>` | 応答せず無視。受信状態は残らない | 次の正常コマンドは正常 |

CR単独は空コマンドとしてdispatcherに渡されないが、無害に破棄されるわけではない。次の文字がLFでなければFRAME異常となり、次のCRLFまでを拒否する。したがって、送信間隔を0.1秒以上にしても、現在の受信処理にある残留状態を解消する条件にはならない。

また、CR待ちが残る間は `has_work()` が真となる。`main.py` はこの条件で戻るため、その巡回の後段にあるRTC時刻採取・SDアイドル処理へ進まない。これはコードから確認した制御経路であり、実機でのSD滞留量やログ破棄発生は未測定。

`INFO` 単体は現在のATEコマンドに登録されていない。情報更新の入口は `INFO_REFRESH`。終端の受理とコマンド名の有効性を分けて評価するため、後続正常コマンドにはNF55Gへ送信しない `*IDN?` を使用した。

## 残す確認事項

- COM20で各終端を確認し、CR単独を0.1秒以上の間隔で定期送信した後の応答と復帰を記録する。
- CR単独受信中のSD処理への影響を実機で確認する。
- CRLF限定を維持したまま空行のCRだけを無視するのか、CR/LF単独もコマンド終端として認めるのかは未確定。分割到着する正規CRLFを壊さないことも確認対象とする。
- この記録では終端仕様の変更、修正済み扱い、実機確認済み扱いを行わない。
