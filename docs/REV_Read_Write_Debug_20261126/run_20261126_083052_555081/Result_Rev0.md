## 実QRと旧QR遅着への処置

| 確認 | 実機結果 |
|---|---|
| Aを同じ受付で2回 | 2回目の受信を確認し、先に確定したAとSS候補を維持 |
| 次の試行でB | 旧IDが失効し、Bの35文字とSS候補50文字が一致 |
| Bを予定した受付にAが遅着 | Aは受付の1,080 ms後に到着。試験プログラムでBの予定原文と比較し、不一致のため `QR_CANCEL`。旧IDは `ERR:QR_STALE_ID` |
| 新しい受付でB | Bの原文・SS候補が一致 |

この遅着対策は、独立に予定ラベルが分かる場合の試験プログラム側の照合。親Picoは遅着Aを一旦登録しており、受付前に開始した読取を親Picoで識別する対策は未実装。同一原文の遅着もこの照合では識別できない。実QRの段階ではSSを送信していない。全試験終了後、COM5から再度D5を読み、REV `A1.<SP>`、LOT `2601`、号機 `000001`、SD OK、ログ欠落0、通信IDLEを確認した。 [実QR一覧CSV](qr_read_results.csv)／[実QRログ](real_qr_wire.log)／[遅着ログ](qr_late_guard_wire.log)／[最終ATE照会](ate_after_restore.json)
