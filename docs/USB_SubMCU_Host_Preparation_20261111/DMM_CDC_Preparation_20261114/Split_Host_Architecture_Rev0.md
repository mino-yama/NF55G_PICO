# QR／7355 Host基板分離 方針 Rev.0

最新追記（2026-11-14）: ユーザーが追加基板をRP2350-USB-Aと明示し、基板USB-A→USB A–Bケーブル→7355 USB-Bで確定。[選定追記](Board_USB_A_Selection_Rev0.md)を優先して併読する。以下の型番・ポート未確定という記述は本追記前の状態。既存QR基板のRP2350-USB-C／Type_C2構成は維持し、追加基板の回路・FW設定・実機適合は別途確認する。

2026-11-19 接続構成の追加確定: 外部測定器用HostはWaveshare RP2350-USB-A（WAVESHARE-30274）。基板のUSB-Cは開発側、USB-AはHost機器側とし、外部測定器のUSB-Bへユーザー準備ケーブルで接続する。給電には外部電源を使用する。ケーブルの型式・結線、外部電源の配線・保護条件、基板個体の電気的受入は別途確認する。

2026-11-14。同一USB Host SubMCU案件の継続。ユーザー指示「もう1台 HOST基板を購入して、PICOとの接続経路を分けましょう」を最新の構成方針として記録する。購入・発注は行っていない。

## 確定した変更

- 既存Host基板はQR専用として維持し、7355用Host基板を1台追加する。
- 親Pico 2と各Host基板の接続経路を分ける。双方向UARTをそれぞれ独立させる設計方針とし、共通線へのTX並列接続や1本の共有バスは採らない。
- 既存QR基板のType_C1を7355用Hostへ変更する検討は中止する。R5／R6の撤去・CC切替回路の施工・そのための写真依頼は不要となる。直前の回路案は履歴として保持し、作業指示には使わない。
- 既存QR基板のType_C2接続・配置済みqr-fixed-20261114.1・既得のQR評価結果を保持する。基板交換・既存FW書換えは今回行わない。

## 新しい構成

```text
ATE ── 既存経路 ── 親Pico 2 ── 既存UART1／RS232C ── NF55G
                       ├─ 独立双方向UART A ── 既存Host基板 ── QR
                       ├─ 独立双方向UART B ── 追加Host基板 ── ADCMT 7355
                       └─ 既存RTC／SD
```

A／Bは説明用で、正式な信号名・ポート番号・ATEコマンド名ではない。親PicoのATE用UART0とNF55G用UART1は転用しない。

|担当|内容|現状|
|---|---|---|
|既存Host基板|QR USB Host・Alt復元|固定接続の限定診断実績あり。正式親子UARTは未実装|
|追加Host基板|7355 USB CDC Host・識別／応答原文取得|型番・個体・USBポート・FWは未確定、未入手|

|ATE|測定条件・製品判定・数値指定の補正書込み指令|従来責任を維持|

## 減らせる課題と残る課題

同じRP2350上でPIO Hostとnative Hostを同時管理する必要がなくなる。固定TinyUSBの単一Host管理に関するUSB-SUB-03は過去構成の技術課題としてOpenのまま保持するが、新構成の成立条件には含めない。構成変更を技術的解決やIssue Closeとは扱わない。

既存QR基板のnative USBとCCを7355向けに改造する必要もなくなる。一方、追加基板のUSB CDC Host適合・CC／VBUS・保護、親Picoの2経路受信負荷、給電容量・GNDは別途確認する。親Picoや電源を共有するため、2台化だけで全故障が相互に影響しないとは保証しない。

## 追加基板の選定条件（型番未確定）

- USB Full-Speed CDC ACM Hostを扱えること。HID専用変換基板では7355を制御できない。
- USB Host用のCC／VBUS供給・電源切替条件を回路図で確認できること。USB端子の外形やHost対応の記載だけで無改造成立としない。
- 親Pico向け3.3V信号の双方向UARTを確保できること。デバッグ・書込みと機器接続の給電が競合しない構成を用意する。
- 既存と同じRP2350-USB-Cを採用する場合は、DMMを追加基板のType_C2へ置く案を検討できる。ただし型番・ポート採用は今回未指定。Type_C2のHost化に必要なCC／D線の処置まで不要になるわけではなく、既存QR基板と同等の施工・受入が必要か個体ごとに確認する。ポート変更は追加基板だけの候補で、既存QRの接続を移さない。

特定製品の在庫・価格・現行版の適合調査や購入推奨までは今回行っていない。

## 親Picoの資源とリンクの設計条件

src/config.pyでATE UART0=57600/8N1、NF55G UART1=38400/8E1を確認。既存ハードUARTは維持する。PIO等による追加の独立双方向2経路を検討し、GPIO・state machine・命令メモリ・IRQ・受信RAM・処理時間を照合してから割り当てる。既存qr_pio_rx.pyはGP9 RX／GP8 idleの旧受信専用試作で、今回の双方向2経路が実装済みという証拠ではない。

経路ごとに起動識別・要求ID・timeout・接続状態・部分受信・取消／遅延応答を管理する。フレーム処理などの共通コードは再利用できるが、状態や未完了要求は経路間で混同しない。QRは現試行・受付要求に対応する完成35文字だけを採用する。測定取得だけでNF55Gへの補正書込みを実行しない。正式コマンド名・CRC・baudrate・ピンは推測で確定しない。

## 次工程

1. 追加基板の型番とHost用ポート・CC／VBUS条件を確認し、必要部品と配線を具体化する。既存QR基板は保持。
2. 新規個体の識別・退避・単体受入後、7355専用Host FWを別成果物で準備する。PCで確認済みのVID:PID=1334:0309、識別Query `*IDN?`＋CRLF、DTR／RTS両ONの実績を出発点とする。Host実機適合は別途検証。
3. 新規Host基板から7355を単独識別し、既知測定条件で読出しを確認する。測定値・前面表示・応答原文を記録。
4. 親Picoの2経路の資源を確定し、各リンクの単体試験、同時通信・片側異常の分離試験を行う。片側timeout／再起動が他方の応答に混入しないこと、ATE／NF55G Timing、Logger非blockingを確認する。
5. 正式QR受付・DMM取得をそれぞれ縦通しする。ATEによる判定・別の数値付き補正書込み指令という境界を維持する。

新基板入手前にも親側の資源確認・リンク設計は進められるが、GPIOや未確定APIを先に実装・確定しない。
