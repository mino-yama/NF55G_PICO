# S1.15_r1 治具側の変更・考慮事項

2026-11-18。製品FW側の確認は設計者が担当するとのユーザー指示に基づき、現行Pico実装への影響を確認した。

## 結論

今回確認した通信・数値変換について、S1.15_r1を理由として直ちに必要になるPicoコード修正は特定されていない。ただし、量産適用前の試験手順・ATE期待値・校正仕様の確定が必要。新版実機の受入完了を意味しない。

| 項目 | 現行治具の確認事実 | 必要な対応 |
|---|---|---|
| SOC上限127% | nf55_decode.py:91–92はsigned8。100%上限の丸めや拒否なし。 | Pico変更不要。ATEの表示・範囲判定・期待値で100超をどう扱うか正式仕様と照合する。 |
| FW版照合 | nf55_decode.py:169はFW_REVを6文字保持。新FWは末尾空白付き `S1.15 `。 | 管理名S1.15_r1と通信文字列を区別。ATE期待値・末尾空白の比較規則を明記する。Picoで版を推測変換しない。 |
| AR REF | nf55_decode.py:347以降はREF8をRAW保持。floatへの自動変換なし。 | デコーダ変更不要。正式AR Query追加時の返却形式・単位は設計回答後に決定。 |
| AD/AR入口 | ARデコーダは存在するが、nf55_command.pyの正式Refresh一覧にARなし。ADの正式制御入口も未実装。 | 校正工程に使うなら新規実装が必要。既存機能の修正とは分ける。要求・応答、T2、校正反映時点を確定後、Code/Test/Docs/CHANGELOGを更新する。 |
| D0取得 | DATA_REFRESHは明示D0。個別QueryはCache参照。D0 T2は300ms。 | CHARGE_ENDを使う工程では最初のD0結果を保持し、同じイベントを見たい間に余分なD0を挟まない。状態監視はD1で足りるか検討。全D0取得禁止や自動再送変更は行わない。 |
| 校正確認 | 製品側の測定補正式が変更。AD応答、AR読戻し、通常測定、外部測定は別の確認対象。 | AD→ARのみで調整完了としない。係数反映条件の設計回答後に、通常測定＋外部測定を確認する工程を定める。自動再起動を追加しない。 |
| SC応答時間 | CLOCK_SYNCのT2は100ms。新版SCはEEPROM保存完了待ちが追加。 | 新FW実機で正常時・他EEPROM処理との競合時を測定。仕様に基づく変更指示があった場合にT2を変更。現段階で独断延長しない。 |
| BC停止・CN/CD | 正常応答は通信成功。既存仕様もSTATUS_REFRESH＋外部測定で動作確認する。BC_STOPはBC0/T2=6000ms。 | 試験シーケンスでSTOPやCLEARのOKだけを動作成立条件にしない。設計回答に沿って停止・充電状態を確認する。Picoによる代替コマンド送信を追加しない。 |
| BBU温度設定 | INFOは値を数値としてデコード。項目別SPは保護設定を拒否。汎用PARAM_SETは50文字形式のみ確認。 | 通常読出しの修正不要。ATEで既定値90℃等を評価する場合は期待値を見直す。上限100℃への変化を理由に項目別保護を解除しない。 |
| その他測定・積算 | 電流/DCIR/積算の出力値に変化。Picoは通信単位の換算を担当。 | 旧FWの実測値を固定期待値に流用せず、同一条件で新FWの受入データを採る。製品PASS/FAILはATE。 |
| EEPROM形式・保護式 | 製品側の設計確認事項。PicoのCache形式とは別。 | 治具にEEPROM移行や製品保護の代替処理を実装する根拠はない。設計回答を受入前提条件として管理する。 |

## 優先順位

1. 新FWを識別するATE期待値と試験ログの版表記を決める（管理名S1.15_r1、通信値S1.15＋空白）。ATE側の実装状況・設定ファイルは今回未確認。
2. D0取得順序とCHARGE_ENDの評価時点を試験手順へ反映する。
3. 新FWでD0=300ms、SC=100ms、BC=6000msの受入を実測する。EB競合も確認する。
4. 校正工程を進める場合はAD/ARの未確定事項を設計者と確認し、正式入口の実装仕様を作る。
5. SOC、温度設定、電流/DCIR、積算値、充電状態のATE期待値を正式仕様に照合する。

## 検証

現行関数を直接実行し、SOCの127/101、FW末尾空白保持、AR REFのRAW保持、SC T2=100ms、AR正式Refresh未登録を確認（5項目成功）。最初の手動入力はREALTIMEを40文字で作成して長さ検証に拒否されたため、規定50文字に直して確認した。製品由来の異常ではない。

前段のHost/Mock354件成功は [検証報告書](Review_20261118.md) とそのログを参照。今回Picoコード変更なし。新FW実機での受入・ATEコードの変更/検証は未実施。
