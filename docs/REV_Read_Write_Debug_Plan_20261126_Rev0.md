# REV読み書きデバッグ計画（2026-11-26）Rev.0

## 確認できた事実

- 参考製品FWは `reference/FW_Review_S1.15_r1_20261118/S1.15_r1/NF55G/src/` にある。FW定義は `S1.15 `。
- `NF55_tbl.c:12`：SSのDATA長は50文字固定。
- `NF55_serial.c:193`以降：規定の位置にETXがなければNAK_ETX。理由コードは `NF55_define.h:313` の0x35。
- `NF55_serial.c:588`以降：SS DATAの50文字はASCII 0x20～0x7Eを検査する。
- `NF55_serial.c:1470`以降：UNIT_REVは受信バッファ位置9から4文字を固定コピーする。3文字の補完処理はない。FFFF指定は変更しない。UNIT_LOTは位置13から4文字、UNIT_SERIALは位置17から6文字。
- 上記SS処理で書き換える製造情報はUNITのREV／LOT／SERIAL。ADU／BBUへ同じ書き込み動作を外挿しない。
- 既存の2026-11-23事前読出し記録の実機FWはS1.14B、UNIT_REVは末尾空白を含む `A5. `。現在の接続実機のFW・元値は試験開始時に再取得する。
- 2026-11-25のポート列挙ではCOM6を確認した。試験当日に再確認する。

## ソースから予想する動作（実機では未確認）

- REVが3文字でSS DATA全体が49文字になるフレームはETX位置異常となり、書き込み処理に進まない。
- 3文字に末尾ASCII空白を付けて4文字にすれば、空白を含む4文字が保存される。
- REVを3文字に詰め、後続項目を前詰めしたまま総長だけ50文字にすると、LOT先頭がREVの4文字目となる。ASCII検査だけでは項目境界のずれを検出できない。
- 末尾空白が格納可能であることと、QRの3文字REVに末尾空白を補う正式な変換規則は別事項。試験結果だけで量産規則を確定しない。

## 明日の試験手順

1. 接続先・現在の製品FW・製品状態を確認する。通信は1件ずつ実行する。
2. D5を明示実行し、100文字の原文と全製造情報を保存する。末尾空白を落とさず、文字数と16進バイト列も記録する。この同一試行の値を復元元にする。
3. QR読取りから実施する場合は、QR原文→解析したREV／LOT／SERIAL→実際に送信するSS DATAの対応を保存する。QR取得だけでは書き込まない。正式入口の現在の実装状況は開始時に確認する。
4. 下表の各試験で送信値を確定し、SSの送受信原文・ACK／NAK・応答・retry・ambiguousを記録する。成功応答だけで書き込み成功と判定しない。
5. 各試験後にD5を明示実行し、REV・LOT・SERIALと、FW_REV・ADU・BBU等の変更対象外を比較する。失敗／成否不明でも元値保持を読み出して確認する。成否不明時の自動再書き込みは行わない。
6. 試験終了時に開始時のUNIT値へ復元し、D5で一致を確認する。復元できなければ実測値と未復元項目を記録する。

| ID | 試験入力 | 確認事項 |
|---|---|---|
| REV-01 | 4文字REV、SS DATA 50文字 | 正常書き込みとD5の4文字完全一致、LOT／SERIALおよび変更対象外への影響 |
| REV-02 | 3文字REV＋末尾ASCII空白、SS DATA 50文字 | 空白を含めた保存と読戻し。表示上のtrimで一致扱いにしない |
| REV-03 | REVを3文字にし、SS DATAを49文字としたフレーム | NAK_ETX（0x35）の予想との比較。D5で元値保持を確認 |
| REV-04 | REVを3文字で前詰めし、末尾で総長のみ50文字に調整 | 項目境界ずれの確認。まずホスト／模擬で送信バイトを検証し、実機で行う場合は直後に元値復元とD5照合 |
| REV-05 | UNIT_REVをFFFF（変更なし指定） | REVを保持できること、他の指定項目の読戻し |
| REV-06 | 開始時に保存したUNIT_REV／LOT／SERIAL | 復元後の完全一致 |

正常長50文字の組立てはFW_REV6＋UNIT14＋ADU14＋BBU14＋予約2。書き込み対象外の指定は既存仕様に従う。故意の49文字送信は通常ATE入口で拒否される場合、治具入口の拒否と製品FWの拒否を区別して記録する。製品FWへの到達が必要な試験は診断経路で行う。

## 2026-11-25追記：試験順序と入力経路の確定

ユーザー指示により、明日11月26日のデバッグを以下の2段階で実施する。現時点は確認手順の整理までとし、この計画更新では実機書き込み・テストプログラムの変更は行っていない。

### 第1段階：複数の疑似QRで書き込み・読み出し

- テストプログラム側で疑似QR入力を選択する。実QRの読取りを必要としない。
- 既存の `tests/test_qr_ss_workflow.py` の受信レコード生成／QRPort注入を参考とする。`FixtureApp` の `qr_transport` に模擬受信部を渡せる構造がある。これはホストテストで使用されている経路であり、現在のPico実機に模擬入力機能が配備済みとは扱わない。通常ATEには専用の疑似QR注入コマンドはないため、実機用テストプログラムで受信部を差し替える準備が必要。
- 現行 `src/qr_write_session.py` の `serial_data_from_qr()` は、QRのREV3文字に末尾ASCII空白1文字を付けてUNIT_REV4文字にする。コード上に2026-11-23承認のコメントがある。本書前段の「正式規則が未確認」という記載は、現行実装確認前の情報として訂正する。
- 使用データは35文字形式を満たす複数件とする。REVだけ変更、LOTだけ変更、SERIALだけ変更、3項目を変更するケースを用意し、先頭ゼロとREV内ピリオドを含める。具体値は実機用テストプログラムで固定し、期待するSS DATA50文字も事前に算出して残す。
- 最初にD5でFW_REV・全製造情報を読み、同一試行の復元元を保存する。
- 各件で新しく受付開始→模擬受信レコード注入→QR_GET?で原文確認→QR_DATA?でSS DATA50文字確認→QR_WRITEを明示実行→INFO_REFRESHでD5読戻し→UNIT_REV／LOT／SERIALと変更対象外の値を照合する。
- QR_SCAN開始前に注入すると開始時の入力破棄対象になるため、必ず受付開始後に注入する。前件の取得IDを使い回さない。同じQRの連続入力でも確認済みデータが後続入力に差し替わらないことを確認する。
- 読戻しは末尾空白を削除せず、元の文字列と16進バイト列で完全一致を比較する。SS成功応答だけで成功としない。成否不明時は自動再書き込みを行わず、D5で状態を確認する。
- 第1段階終了時に開始時のUNIT製造情報へ復元し、D5で確認する。

### 第2段階：実QRの読み取り

- 第1段階の書き込み・読戻し確認後、テストプログラム側で実QR受信部へ切り替える。
- 実QRを読み、原文35文字、解析したREV／LOT／SERIAL、末尾空白付与後のSS DATA50文字を照合する。複数枚と同一QRの連続読み取りで、前件混入・取り違えがないことを確認する。
- この段階の対象は実QRの読み取りと送信予定値の確認まで。読み取っただけでSSを書き込まない。

### 桁不足の異常系との区別

通常の疑似QR入力も実QR入力もREV3文字から末尾空白付き4文字を生成するため、REV-03（全体49文字）／REV-04（項目境界ずれ）は通常のQR経路からは生成されない。これらは別の診断用フレーム生成による異常系として区別し、疑似QRの正常な書き込み・読戻し試験結果と混同しない。

## 2026-11-25追記：REV桁数を重点とした結果・ログの提出方法

ユーザー指示：特にREVの桁数の違いによる読戻しを中心に確認する。最終の良否はユーザーが行う。テストプログラムは良否を確定せず、実測結果と対応するログを提出する。

### REVの重点確認

- 入力QR内のREV文字列／文字数、変換後のSS UNIT_REV文字列／文字数、実際の送信バイト、D5読戻しのUNIT_REV文字列／文字数を一列に対応付ける。
- 通常QRはREV欄3文字固定、SSとD5のUNIT_REV欄は4文字固定。通常経路の「3文字＋末尾空白」と、診断経路の「REV欄の文字数不足」を別ケースとして記録する。
- 疑似QRで複数のREV値を用い、末尾空白込み4文字への変換と読戻しを確認する。診断経路では4文字REV、3文字＋空白、全体49文字の短いフレーム、全体50文字だが項目境界がずれたフレームを比較する。QR欄に直接4文字REVを入れるケースは35文字の正常QRとは扱わず、形式検査の結果として区別する。
- 空白は画面上では `<SP>` と明示し、別に文字列のrepr表現と16進バイト列を保存する。比較時にstrip／trimしない。
- 各ケースは直前D5→書き込み送信→直後D5の順に記録し、REV以外のLOT／SERIALのずれや変更対象外への影響も示す。復元時も送信と読戻しの記録を残す。
